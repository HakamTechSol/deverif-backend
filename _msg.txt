Assets module: schema, service, routes, and DB-level constraint tests

Four tables (asset_categories, assets, asset_assignments, asset_maintenance) with
the status column derived rather than client-writable, so an asset's state cannot
contradict the rows beside it.

THREE SCHEMA BUGS FOUND BY TESTING AGAINST A REAL DATABASE, not by reading the
SQL. Each is documented at its migration.

1. The obvious uniqueness key did not work. UNIQUE (asset_uuid, returned_at) was
   meant to enforce "at most one open holder", but an open row has
   returned_at = NULL and NULLs do not collide in a MySQL UNIQUE index. Two open
   assignments were ACCEPTED - the worst possible error in an asset register. Fixed
   with a generated column that is a non-NULL constant only while the row is open
   (20261110b), the same technique already used and verified for maintenance jobs.

2. Cross-tenant category links were possible. The category FK only proved the
   category existed, not which tenant owned it; an asset in org B could point at
   org A's category. The service did check this, but multi-tenancy cannot depend on
   every caller remembering to scope. Replaced with a composite
   (category_uuid, organization_id) foreign key (20261110c).

3. That fix then broke organization deletion. RESTRICT makes MySQL cascade to a
   tenant's categories, refuse the category delete because assets point at it, and
   abort the whole operation - so data erasure and offboarding became impossible.
   MySQL cannot express "restrict unless the owning org is going away too", so the
   FK is CASCADE and the protection moved to the service, which refuses to delete a
   category holding assets with a 409 naming the count (20261110d).

Every mocked test in this suite passes while a broken endpoint 500s, because
pool.query returns rows for any string. So assets.db.test.js exercises the real
database for the invariants only the schema can enforce, and skips rather than
fails when no database is reachable. Two of the three bugs above would have shipped
green under mocked tests alone.

On the service: status is never accepted from a request body. Every mutation
recomputes it from the open assignment and maintenance rows, under FOR UPDATE, so
concurrent clicks cannot both read "available" and both proceed. Maintenance
outranks assignment; retired is terminal. A return flagged damaged or
needs_maintenance opens a repair job in the same transaction, because an asset
coming back broken and sitting in "available" until someone notices is how broken
equipment reaches the next person.

One design note: buildInsert deliberately refuses organization_id, uuid and
created_by_uuid so a caller cannot inject a tenant or forge an audit author.
composeInsert keeps those server-side values strictly separate rather than
defeating the guard.

16 routes registered under the existing asset_management module flag. Category
administration is org_admin-only; moving stock is not.
